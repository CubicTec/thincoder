# Thincoder Server —— 项目需求

> 板块 = server ∥ 组件落点 = `thincoder/thincoder-server/`（子目录形式）∥ 本档 = 需求档（五要素已齐）。

## 1. 总体目标

**模块目标**：为 ThinCoder 开发团队提供统一的模型 token 网关——集中凭证、计量、配额，数据不出内网；后续逐步增加团队协同能力。

**服务对象**：开发团队（内部工具面，非对外产品）。

**形态**：内网（团队）一台服务器上常驻，团队内网可达；**公网化 = 必要**（用户裁——连手机/外网可达所必需；威胁模型按 **公网** 计：TLS ∥ 鉴权加固/限流 ∥ 审计面三件前置）。
**部署（未来计划——用户澄清：「几台」= 一台做 server，几台跑 runner）**：**阿里云 ECS = 1 × server（单实例）+ N × runner**；**server 不做多实例/负载均衡**（已核：服务端存储 = SQLite 单文件 WAL——单库单写者，现设计如此）；
**runner 无需公网入向端口**（server → 节点 Docker API `:2375` 仅内网/安全组可达，节点不开任何面向公网的端口）⇒ **只有 server 那一台需要公网 IP + 证书**；执行面（runner）= 同云数台 Docker 节点，与控制面/执行面分离相容。
**TLS 内置（用户裁：「没有 nginx，thincoder-server 要自己实现 tls」）**：**无 nginx ∥ 无前置反代**——**server 自身实现 TLS**（实现面 = Node 内置 `node:https`/`node:http2` + 证书——**零第三方运行期依赖不破**）。
连带两项：① 配置面新增 TLS 键（证书/私钥路径等）——沿「**每配置项有界面写入口**」口径，控制台须有对应写面（重启生效）；② 既有「服务不内置 TLS / 前置反代」口径与 nginx 样例（`thincoder-server/README.md` §11 ∥ `ops/OPS.md`）**归设计轮随正**。

**演进方向**：第一步 = token 网关（已上线）；**第二步 = 团队协同（范围与顺序见 §2 功能点 31–35）**：

- **基础件**（三端共用）= 客户面接入与登录（端侧直登 ⇒ 自动添加指向本 server 的 provider；**登录态 = 团队功能开关**——功能点 31）；
- **前置件（在团队台账之前——用户裁）** = **团队项目与权限**：项目管理界面（git 仓登记 ∥ 项目成员 ∥ **负责人**）+ 权限与可见性模型（跨面统一判据——台账 ∥ 记忆 ∥ 在场 ∥ 会话 ∥ 控制台）；用户原话：「我甚至觉得这个问题应该在团队台账之前要明确，否则团队台账会缺一块基础。」（功能点待裁——现 §2 的 31–35 不覆盖本件）；
- **四面**：① 团队台账（团队一本账）② 团队记忆与知识库（team 层重规划——personal/project 零改；**载体重构方向 = 数据库**（弃现行 git 仓同步）——用户裁「团队记忆需要重构，原来那种git方案我不喜欢，希望改走数据库。」；**客户端（三端 CLI/VSC/桌面）将来 = 本地记忆 + 团队记忆双支持**〔对照：成员面只走团队——功能点 50 ⑧〕）③ 在场与通知 ④ 会话协同（**排最后**）；
- **一缓**（条件复核）= 规范与技能下发（团队资产库）——用户裁「先缓缓」（现可由 git 入库实现）；复核条件 = 出现**跨仓统一** ∥ **规范/技能不能入库**的实需；
- **贯穿纪律** = 端侧同批（三端 + 控制台同批落齐（禁「先行后补」））∥ 本机面不夺能力（§3——团队面不做离线缓存）。

**第三步 = 服务端开发（已立案——用户「开」；功能点 50 ∥ AC-50；设计轮在途）** = **服务端开发**：git 仓可直接拉到 server；用户 **web 登录后直接由 server 端 agent 完成开发**；未来支持**移动端 app**。骨架已裁项与待设计五题 = §5「工作区内的开发」行（逐题出案）；父侧建议：B5（会话协同）设计须与「服务端 agent 会话」形态**相容**（不封死）。
**立案依据**：用户追裁（原话「成员面的会话是不是可以做起来了？我希望能够考虑周全点，界面跟vsc和桌面基本一致。」）+「开」——界面一致 = 与 VSC/桌面 基准对照（实走终判），「考虑周全」= 待裁五题逐题出案。

**关系面**：独立新件。与既有 `ai-gateway` 不耦合、无收敛计划；其设计与实现经验可作参考。

**形态决定（已定）**：server 落 **`thincoder` 仓子目录**——`thincoder/thincoder-server/`（与 `thincoder-core` ∥ `thincoder-cli` ∥ `thincoder-vscode` ∥ `thincoder-desktop` ∥ `thincoder-render-core` 同级）。

依据：

- 本仓**分仓例外论**（拆仓只为例外：独立部署 ∥ 独立发布 ∥ 独立生命周期——server 三条均不成立）；
- **先例方向 = 收敛**（VSC 仓经 subtree 并入本仓——走回头路无益；且每仓需自持一套 AGENTS ∥ 文档 ∥ 台账 ∥ manifest ∥ 批次流程）；
- **协议耦合**（server 大概率直用 core 协议/类型/逻辑——同仓直连 import；协议两端可一提交同改同审）；
- **发布面不构成拆分理由**（单仓多产物已跑通：npm cli ∥ vsix ∥ 桌面安装包——server 只是又一产物，从子目录部署）；
- **可逆性不对称**（先同仓后分 = subtree split——易；先分后并 = VSC 并仓代价——贵。低后悔路径 = 先同仓）。

**例外重启条件**（满足其一再议单仓）：① 真·独立生命周期（他人维护 ∥ 独立对外版本且与客户端解耦 ∥ 不依赖 core 的异栈）；② 硬隔离需求（如对外开源/外发——subtree split 亦可解）。

## 2. 功能性需求

**第一步 = token 网关，功能点三十条**：

1. **统一入口**：真实 provider key 只存网关；团队成员持团队 key + 网关地址接入。成员机器不再放真 key。
2. **OpenAI 兼容面**：`/v1/chat/completions`（SSE 流式）。ThinCoder 四端以 `baseURL` 指入即用；其他 OpenAI 兼容工具同。
3. **计量**：逐请求记录（成员 × 模型 × 时段 × token 数），供计量看板查询。
4. **配额**：按成员设额度；超额 = 拒 + 明确提示。
5. **凭证管理**：团队 key 签发/吊销；上游 provider key 配置。
6. **向量接入面**：`/v1/embeddings`（OpenAI 兼容），数据不出内网。旁路引擎（Ollama / TEI 等内网独立进程）承载推理；网关只做协议面与记账；引擎起停手动。**嵌入配置可选**（缺位 ∥ `null` = 禁用态：服务照常启动；`/v1/embeddings` 明确报错）；**引擎模型不入通用模型清单**（单独命名空间——`/v1/models` 与控制台服务模型页只列 chat 模型）。
7. **轻量账号体系（B 案——用户定）**：成员 = 账号（用户名 + 密码散列）；角色 admin ∥ user；**网页登录**——成员自助取/换个人 key + 看自己用量 + **自助改密**（用户定）∥ admin 登录管成员/配额/吊销（现看板升级为受门禁的管理页）；
   首个 admin = 首启引导（env 或本机 CLI）；运维 CLI 降为服务器本机兜底。**admin 重置成员密码 = 在**（用户定——忘密兜底）；**形状 = 定稿**（AC-7 已落——设计 `accounts/ACCOUNTS.md` §5 七判据）。
8. **分发与部署（用户定——「支持 npm 发布和 docker 方案」）**：**npm 发布**（包名拟 `@thincoder/server`——装机 = `npm i -g`）+ **Docker 镜像**（Dockerfile ∥ compose 样例）两路；守护 = systemd（裸机路）∥ docker restart 策略（容器路）；**入发布序列**（RELEASE.md 扩展 = 随发布面轮）；registry ∥ 首版号 = 部署时确认。（AC-8 已落——见验收表。）
9. **provider 预设（用户定——「我希望加」）**：server 配置支持**内建 provider 预设**——管理员按预设名添加常用上游（免手写 `baseURL`（预设不携模型））；预设覆盖范围与配置形态 = 设计轮定（**形态 = 定稿**：server 自持表——KD-SV-17 ∥ 起步 21 家 OpenAI 兼容子集）；零第三方运行期依赖（沿 §3）。
10. **自动更新（用户定「server我也希望实现自动更新，那docker里的也能吗？」+ 裁「用不用容器都走npm路径升级，容器只做个壳就行」）**：
   **两路统一走 npm 版本身份与升级路径**——版本身份 = npm 包（`@thincoder/server`）；**容器 = 壳**（镜像 = node + 引导层——App 代码由 npm 取装，容器不自带版本身份）；
   **形态 = 定稿**（设计轮：`autoUpdate` 三档默认 `notify` ∥ 壳收敛 `TC_SERVER_VERSION` 三态 ∥ ready 行版本可见性——KD-SV-18；机制全文 = 设计 `ops/OPS.md` §5.4）；升级 = 装 npm 新版 + 重启；回滚 = 版本回指 + 重启；前置 = 发布面上线（registry 有新版本源）。
11. **控制台 provider/模型管理（用户定——「开啥玩笑！你觉得这是一个产品该干的事儿吗？！」）**：provider 与模型的配置管理**必须上控制台**——管理员在界面里增删改 provider、选/开放模型，**不再只靠 `config.json` + 重启**；
   与 `config.json` 的关系（迁入 ∥ 主从 ∥ 过渡期并存）= 设计轮定；密钥落服务端形态 ∥ 模型发现（调上游列真实模型）与勾选开放 ∥ 生效方式（热生效 ∥ 保存即重载——现行「配置不热载」口径随设计收正）∥ 与预设面的衔接 = 设计轮定（**形态 = 定稿**：库单源 + `config.json` 降为一次性种子 ∥ 保存即热生效——KD-SV-19；机制全文 = 设计 `gateway/API.md` §2.2 ∥ `ops/OPS.md` §1）。
12. **首版完备化（用户定——「好歹像个完整的产品！你自己先反省一下，看看还漏了什么，都给补齐了」）**：补齐清单——
    ① **健康检查面**（`/healthz` 现全树零命中；接线 = Dockerfile HEALTHCHECK ∥ compose ∥ 排障）；② **登录防爆破**（登录尝试零限流——零命中；退避/锁定 + 事件日志；防枚举口径保留）；③ **控制台版本与更新可见**（现控制台零版本面——零命中；顶栏/页脚版本 + 更新可用提示，接更新状态）；
    ④ **成员接入指引**（README/控制台无「客户端指入」成文）；⑤ **部署文档完备**（反代样例 ∥ 备份口径增强——现仅手工 cp）；⑥ **用量保留口径**（用量表只增不减——实核；保留窗/清理 = 设计轮定）；形态细节 = 设计轮定；
    杂项（用户裁）：**LICENSE = MIT**（仓根 ∥ 包内落地）∥ **favicon = 桌面在用图标**（`thincoder-desktop/build/icon.png`——控制台接入）∥ **i18n = 要 ⇒ 独立入面（§2:13）**。
13. **控制台多语言（用户定——「多语言要」）**：控制台界面（侧栏全量——登录 ∥ 我的六页 ∥ 管理十页——与提示文案）支持**中文 ∥ English**——
    联动机制（浏览器语言自动 ∥ 显式切换）∥ 文案表形态（前端静态表 ∥ 后端下发）∥ 后端 API 错误消息策略（错误码 + 前端映射 ∥ 双语字段）= 设计轮定
    （**形态 = 定稿**：前端静态表三档 + `localStorage` 记忆 + 自动/显式双联动 ∥ 错误码前端映射（服务端消息中文单语零改）——KD-SV-26；全文 = 设计 `webui/I18N.md` §2.1）；
    文档面多语言（README 英文）不在本条（另议）。
14. **控制台信息架构与导航重规划（用户定——「功能/页面/导航，好好规划组织一下，现在这么把功能随便一堆，堆在一个页面上的做法，真的不专业，会被用户笑话」）**：控制台**不得单页堆叠**——功能分组上导航（分区 ∥ 一页一职责）；信息结构建议形（设计轮定稿）：我的（key ∥ 用量 ∥ 账户设置）∥ 管理（成员 ∥ provider 与模型 ∥ 用量统计 ∥ 系统[版本/更新/接入]）；
    路由/导航形态 = 定稿（**侧栏十六页** + hash `#/<组>/<页>` + 旧链重定向 + `nav.mjs` 纯函数——KD-SV-20；全文 = 设计 `webui/WEBUI.md` §2）；**控制台面统一服从本轮定稿的 IA**。

**15. 控制台可见面完备化二轮（用户定——「这些先落地，以上全做，做完我再看」；承走查「需求覆盖程度不高」+「向量模型完全没有落地面」）**：六面——
    ① **向量服务可见面**：系统页新增「向量服务」卡（引擎地址 ∥ 模型名 ∥ 可达性状态 ∥ `/v1/embeddings` 调用 snippet ∥ 用法一句）+ 试跑（短文本 ⇒ 维度 ∥ 耗时——不落库不计量）+ 用量面 endpoint 区分（chat ∥ embeddings——明细列 + 过滤）；**未配置态**（缺 `embedding` 段 ⇒ 三输入空 ∥ 状态行「未配置」∥ 保存 = 从无到有创建段）；
    ② **用量看板升级**：明细表之上加——时间趋势（按日）∥ 按模型/成员聚合 ∥ top 排行 ∥ 导出（CSV/JSON 下载）；
    ③ **管理总览**：新 `/admin/overview` 为 admin 落地页——今日请求/token ∥ 成员数 ∥ 服务与 DB 健康 ∥ 更新提示 ∥ 快捷入口；旧 `/admin` 重定向；
    ④ **审计/安全面**：安全事件落库（登录成/败/锁定 ∥ key 轮换/吊销 ∥ 密码重置/自助改密 ∥ 成员创建——「删除」全库零既有路径，未入册；如需 = 新需求点）+ `/admin/audit` 列表（过滤：类型/成员/时段）；
    ⑤ **健康可见**：侧栏 meta 槽状态灯（`/healthz` + DB）+ 系统页健康块 + 自动刷新；
    ⑥ **key 细节面**：key 列表加「最后使用时间 ∥ 最近用量」（usage 表已带 `key_id` 归因）；
    形态细节 = 设计轮定（端点形 ∥ 图表手段（零依赖——SVG/纯 CSS 手绘）∥ 事件表形 ∥ 保留窗衔接）。**边界**：引擎起停仍手动（可见面 ≠ 管理面）∥ 不做告警推送 ∥ 不加图表库（零依赖沿 §3）∥ 不改 embeddings 转发/计量语义。

**16. 控制台弹窗交互（用户定——「用户管理界面，我觉得应该用弹窗打开用户详情以后编辑修改，另外，弹窗我建议你做成一个公共组件，因为后续肯定会铺天盖地的使用弹窗」）**：① **成员弹窗（详情 + 新建）**——成员管理页点击成员 ⇒ 弹窗展详情 + **编辑修改**（现行成员操作〔设额度 ∥ 重置密码 ∥ 逐 key 吊销〕迁移入弹窗语义）；**新建成员表单同迁弹窗**（用户定——「新建成员当然也要进弹窗」）；
    ② **公共弹窗组件**——控制台自持共享模块（遮罩 ∥ 关闭语义 ∥ 键盘/焦点 ∥ 复用 API——供后续各页铺开）；形态细节（组件 API ∥ 保存/取消语义）= 设计轮定。**边界**：其他页迁移不在本条（按需后随）∥ 零依赖 ∥ 零构建不变。

**17. 服务模型页（用户定——「提供服务的模型我认为应该单独放一个页面，列表列出所有提供服务的模型，同样也应该是弹窗查看详情，修改配置，虽然我现在还没想好应该配置什么」）**：① **独立页「服务模型」**——列表 = 网关对外服务的全部模型（与 `/v1/models` 同源——`provider/model` **chat** 清单——嵌入模型不入本页）；② **弹窗详情/配置**——点击模型 ⇒ 弹窗（复用公共弹窗组件——功能点 16②）展详情 + 修改配置；
    **可配置项 = 已裁（用户——「ACDE」）**：A（开放/停用——**独立保留、不得被 Provider 页吸收**：上游模型退役后从发现列表消失，Provider 页勾选不到，退役模型的开关只能在服务模型页操作——开放清单的**自持操作面**；用户裁）∥ C（per-model 限流）∥ D（展示元数据）∥ E（成本权重）；
    **B（默认请求参数）不选**；实现序 = **已排**（设计在盘）。**边界**：模型目录来源不改（provider 配置派生）∥ 零依赖 ∥ 零构建不变。
**18. Provider 管理面重做（用户定——「Provider与模型我希望改成 Provider，页面上就显示 Provider 列表，现在添加 Provider 的方式很奇怪，我希望改成点击添加按钮弹窗添加，Provider 列表点击弹出详情页，上面是 Provider 的基本信息，下面是提供的模型的列表，用户可以勾选，选中的加入服务的模型」）**：① 导航项与页面标题收正为「Provider」；页面 = Provider 列表（行点击 ⇒ 弹窗详情）；
    ② **添加** ⇒ 页首「添加」按钮 + 弹窗（预设快速添加 ∥ 手写两径——现内联添加面撤除）；③ **详情弹窗** = 上部基本信息（名 ∥ baseURL ∥ key 态 ∥ 测试连接）+ 下部**模型勾选列表**（候选来源 = **上游发现**——用户裁「上游发现，不用手动补充」；勾选态 = 现配置 `models`；发现失败路径处置 = 设计轮按此定）

## 3. 非功能性需求

- **安全**：仅内网可达（bind 内网接口）；**真实 provider key 只存网关**（成员侧零真 key）；团队 key 逐人签发/可吊销。
- **性能**：流式转发（SSE 逐块透传——不整段缓冲）；单机常驻（团队规模级并发）。
- **依赖纪律**：沿本仓纪律——**零第三方运行期依赖**（node 标准库为主；存储候选 = `node:sqlite`）。
- **可靠性**：常驻进程（崩溃恢复 ∥ 开机自启 = 部署面——**薄面已落**：`ops/OPS.md` §5（systemd ∥ 容器 restart 两路））。
- **增长规划（用户令——server = 长期平台，未来功能与规模均会大幅增长）**：架构须为增长**留对断点**——路由注册制（新端点零改主干）∥ 存储迁移链（`user_version` 逐版可迁）∥ 会话无状态倾向（多实例就绪）∥ 模块边界可拆 ∥ 配置面段形可扩；**演进写法 = 触发条件式**（多实例/协同/对外各有触发条件与决策点，见设计档）；**不为未来预建**（队列/缓存/拆分/插件/ORM 一类不落）；
- **端侧同批纪律（用户裁——团队协同面通用）**：任何端侧能力面必须在**同一批**落齐 CLI ∥ VSC ∥ 桌面 + 相应控制台页——**禁「先一端、后同步」**（用户原话：「先行下次同步你肯定做不好，丢三落四的，我已经吃过几次亏了」）；
- **本机面不夺能力（用户裁）**：**个人台账 ∥ personal/project 记忆**的本机读写不经网络照旧；**团队面不做离线缓存**（用户原话：「没必要支持离线缓存，因为我们是 agent，离线了咋用啊！」）——未登录/断网 ⇒ 团队面（团队台账 ∥ team 记忆 ∥ 在场/通知…）不可用，本机面照常（与功能点 31③ 同拍）；
- **客户端认证面**：客户面凭据 = 登录 token（功能点 31）；真实 provider key 只存网关不变。

## 4. 不做项

- 不做**对外销售/计费**（那是 `ai-gateway` 的域——本件 = 团队内部）；
- v1 不做**多租户**；
- v1 不做**模型路由**（已降级为后续可选）；
- v1 不做**非 OpenAI 协议的翻译**（只 OpenAI 兼容面）；
- v1 不做**配额阈值告警**（80% 等——暂缓，后续再加）；
- v1 不做**嵌入引擎的起停管理面**（引擎进程 = 手动起/停；可见面/用量/试跑 = 在——功能点 15①）；
- v1 不做**独立客户端管理台**（管理面 = 内嵌网页（B 案）——不做桌面/独立应用形态）；
- v1 不做**组织架构同步 ∥ SSO ∥ 双因素 ∥ 密码找回**（「找回」需外部通道（邮件/短信）——留「团队协同」步；**改密 = 在**）；
- 团队协同面不做：**代码托管/评审**（git 的域）∥ **即时通讯群聊**（只做与任务相关的通知）∥ **CI/CD 编排** ∥ **多组织/多租户**（单团队内部起步——沿「v1 不做多租户」）；

    - **出站规则 = 两类同表（已退场）**（用户裁「默认全拒 + 白名单」；用户提「应该用 IP 地址段更符合行为习惯，有点像阿里云的安全组配置」⇒ 采为**一等规则类**）：
      - **阶段性状态（用户裁——整套摘除）**：出站管控（闸本体 ∥ 规则面 ∥ 待批队列 ∥ 成员提示）经用户裁定**整套摘除**（D1 = 不留开关/骨架）；下方 ①/②/通配/待批机制条目 = **退场留档**（复建/启用须另批新裁）；沙盒网络面现状 = **盒直连出网（零管控）**。
      - **（以下机制条目 = 退场留档；复建/启用须另批新裁）**：
      - **① CIDR 规则（网络层——安全组同形）**：`allow ∥ deny` × `CIDR[/端口]`；**L1 门级不变量**（非行、不可改、不可绕）= 回环 `127.0.0.0/8` ∥ 链路本地与云元数据 `169.254.0.0/16`；**L2 默认禁单**（种子 deny 行——可被显式 allow 开）= RFC1918 私网 ∥ 服务器自身网段 ∥ 节点登记网段；内网∕固定 IP 后端 = 显式加 CIDR 允许条目（零域名依赖）。
      - **① 续 · 强制面**：L1 命中即拒零挂起 ∥ L2 可被显式 allow 开（U2-A 不变）；「强制」= 全协议/全端口 ∥ 双径同判 ∥ 解析零地址 ⇒ 拒 ∥ 节点网段登记幂等带入 ∥ 闸为盒前置（fail-closed）；求值与定义单源 = 设计 `sandbox/SANDBOX.md` §4 强制面块（总序 = L1 ≻ 零地址闸 ≻ 内置允许 ≻ L2 ≻ L3）。
      - **② 域名规则（应用层——经代理）**：公网服务按域名放开（父侧本机实测：`registry.npmjs.org` ⇒ Cloudflare `104.16.x.x`（共享 CDN 段）∥ `raw.githubusercontent.com` ⇒ `185.199.108-111.133`（GitHub Pages 段）∥ `github.com` ⇒ Azure `20.205.x`（动态）——**公网服务 IP 共享且漂移：按 IP 放开等于放开 CDN 全网，紧打 IP 又随换 IP 失效**，故域名规则不可省）。
      - **两道闸次序**：域名命中 ⇒ 解析 ⇒ 解析出的 IP **仍须过 CIDR 闸**（否则「白名单域名 + 内网解析」即绕过）；**冲突**：deny 恒先于 allow。
      - **控制台按安全组式呈现**（方向 ∥ 协议 ∥ 端口 ∥ 目标 ∥ 动作 ∥ 优先级 ∥ 备注）；增删即生效（不重建盒）+ 每次增删记审计行；默认单开箱可用（git ∥ registry ∥ 常见 CDN）；「谁能改」归权限模型。
      - **① CIDR 规则与 ② 域名规则各自可单独使用**：只用 CIDR（零域名依赖，利内网/固定 IP）或两者并用。
    - **通配符**（用户问——适用于 ② 域名规则）：支持**单层左通配**（`*.example.com`——恰一级子域；要更深就写 `*.a.example.com`）；**禁**裸 `*` ∥ TLD 级通配（`*.com` 类）∥ IP 段通配（CIDR 规则走显式段，不用通配符）；**命中在解析后的 IP 上二次校验**（通配域名解析到 `127.0.0.1` ∥ `169.254.*` ∥ 内网段 ⇒ 照样拒）；通配条目在控制台带醒目标记 + 审计行记原文。
    - **首次新域 ⇒ 待批队列（已退场）**（依据行业形补——Claude Code 沙盒同形：新域名提示批准、「是，别再问」入档；实例：`code.claude.com/docs/en/sandboxing`）：盒访问未在白名单的域 ⇒ 请求**挂起**，控制台出现「工作区 X 想访问 Y」⇒ 一键 **批准一次 ∥ 批准并记住 ∥ 拒绝**（三次批准同一域 ⇒ 当次记一行建议入默认单）；超时（默认 60s）⇒ 拒。默认单开箱可用——装依赖/拉仓无需任何批准。
    - **资源上限 + 墙钟 TTL**：cpus ∥ memory ∥ pids ∥ 磁盘配额；空闲超时即拆；**容量键 = `maxBoxesPerRunner`（单节点盒数上限——缺省 8）∥ 节点侧根路径键 = `workspaceRoot`**——全局默认 + 每工作区覆写，各有 UI 写入口（单源 = `sandbox/EXECUTION.md` §3）。
    - **非目标（明写不做）**：内核 0day ∥ 侧信道 ∥ 国家级逃逸（要挡须另立级）。
